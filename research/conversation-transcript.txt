ADR-0002: Jinja2 for HTML Templating
Status:   Accepted
Date:     2026-03-15
Author:   Automation Team

CONTEXT

The original MultiTableProcessor design used an HTMLGenerator class
that built HTML table strings in Python by concatenating strings and
substituting named placeholders into a template file. That approach
had two compounding problems: HTML logic lived in Python, and any
change to the output structure required modifying Python code rather
than the template.

The quality requirement driving this decision:

  TAG:       Maintainability.Template.EditTime
  SCALE:     Minutes for a Python engineer with no HTML experience
             to change a column in the rendered table output,
             measured from reading the task description to a correct
             browser render
  METER:     Observed time in developer task timing with
             representative config
  CURRENT:   Not measured formally; estimated 20-30 minutes with
             string concatenation approach due to HTML scattered
             across Python methods
  TOLERABLE: 15 minutes
  GOAL:      5 minutes
  STRETCH:   2 minutes (edit the template, re-run, done)

A second requirement was output safety. User-sourced data from Excel
files is untrusted. The dashboard rendering must not introduce XSS
vulnerabilities regardless of what cell values the source data
contains.

  TAG:       Security.Output.XssRisk
  SCALE:     Number of rendering paths where user-supplied data
             reaches HTML output without escaping
  METER:     Code review counting paths from read_excel_files() to
             final HTML string where escaping is not applied
  TOLERABLE: 0
  GOAL:      0

DECISION

HTML rendering uses Jinja2 via TemplateProcessor.render(). The
HTMLGenerator class was removed. The template lives in
web/template.html and receives a context dict from
MultiTableProcessor.generate_html(). CSS and JavaScript file
contents are loaded by TemplateProcessor.load_file() and marked safe
explicitly. All user-sourced data passes through Jinja2's autoescape
mechanism. No HTML string building occurs in Python.

REASONS FOR THIS DECISION

Separation of structure from logic: HTML structure belongs in an
HTML file. The template loops over tables and hvt_rows directly
using Jinja2 for-loops. A front-end change (adding a column,
changing a CSS class) is a template edit, not a Python edit.

Security by default: Jinja2's autoescape=True means every value
rendered from the context dict is HTML-escaped unless explicitly
marked safe. The only values marked safe are CSS content and
JavaScript content, which are read from controlled files in the
web/ directory, not from user data. This gives XssRisk a measured
value of 0 rendered paths without escaping for user data.

Tested ecosystem: Jinja2 is the standard templating library for
Python web and document generation. It is already a dependency of
Flask and Ansible; it is unlikely to become unmaintained. The
autoescape feature is well-documented and audited.

Reduced Python complexity: Removing HTMLGenerator simplified
generate_html() from a method that built HTML strings to a method
that assembles a context dict and calls render(). The context dict
is easy to unit-test independently of HTML output.

Template readability: A Jinja2 template reads as HTML with clear
loop markers. An engineer familiar with any modern templating system
(Django templates, Handlebars, ERB) can read web/template.html
without Python knowledge. This matters for handoff to a front-end
specialist in Phase 2.

CONSEQUENCES

Positive: HTML structure is editable without touching Python. XSS is
prevented at the rendering layer for all user-sourced data. The
template is readable by engineers who know HTML but not the Python
codebase.

Added dependency: Jinja2 is listed in requirements.txt. It was not
required in the original string-substitution approach. This is an
accepted trade-off: Jinja2 is a mature, maintained library used
across the Python ecosystem and is already transitively present in
many Python environments.

Template as a deployment artifact: web/template.html is a required
runtime file alongside the Python source. Deploying the dashboard
generator requires deploying the web/ directory. This is documented
in docs/README.txt.

Marked-safe discipline: Engineers adding new CSS or JavaScript
includes must use Markup or the |safe filter explicitly and must not
apply it to any user-sourced data. This convention must be
understood and followed. It is documented in
docs/HOWTO_NEW_ENGINEER.txt.

MIGRATION TRIGGER

Revisit this decision if:

1. A second templating library is proposed for a subsystem (for
   example, for email report generation). Standardize on one library
   rather than introducing a second.
2. Phase 2 moves to a web framework (Flask, FastAPI, Django) that
   bundles its own templating system. Jinja2 integrates natively
   with Flask and FastAPI; no migration is needed in that case.
3. A security audit identifies a path where user data reaches a
   |safe filter or Markup() call. That is a code defect to be fixed,
   not an ADR revision.

Air-gapped + "use the latest" + "hate pinning": These are in tension
and I want to be explicit about the trade-off rather than paper over
it. Here's the practical reality:

In a connected dev environment, requirements.txt listing jinja2
(unpinned) works fine - pip resolves to current. In an air-gapped
target environment, the wheels you ship are what's available.
Period. So the question is really "where does pinning happen, and
who does it?"

I'd propose this pattern, which I think respects your preference
without lying about the constraint:

- requirements.txt - top-level direct dependencies only, unpinned or
  loosely bounded (e.g., jinja2>=3.0). This is what you maintain by
  hand. Stays clean and readable.
- requirements-lock.txt - generated from pip freeze in a known-good
  environment at release time. Fully pinned with versions, optionally
  with hashes. This is the air-gap shipping manifest, not something
  you edit.
- Wheelhouse - a directory of .whl files matching the lock file,
  shipped alongside for pip install --no-index --find-links
  ./wheelhouse -r requirements-lock.txt.

You hand-maintain the unpinned file. The pinned file and wheelhouse
are build artifacts produced by make wheelhouse at release time.
You're not pinning during development; you're snapshotting at
release. Different activity, different file. Does that frame the
trade-off in a way that works for you?

For handling "needed version isn't available" in the air-gapped
environment: that's a release-time problem solved by building the
wheelhouse against the target Python version on a connected machine,
then transferring the whole wheelhouse. If a wheel doesn't exist for
the target platform, you find out at build time on the connected
side, not at install time on the air-gapped side. The install guide
says "extract, pip install --no-index --find-links wheelhouse -r
requirements-lock.txt" and that's it.

FIPS + SQLite for PoC: Worth knowing - SQLite itself isn't FIPS-

a "FIPS gotchas" note: avoid hashlib.md5 even for non-security uses
like cache keys (use hashlib.sha256 or hashlib.blake2b), avoid

any added dependency doesn't bundle its own SSL/crypto. Sound right?
