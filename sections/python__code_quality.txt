Python Code Quality Tools


STANDARD TOOLKIT

The goal is one consistent set of tools across all Python projects. Building familiarity
with the same tools on small projects pays off when applying them to large ones.
All tools listed here are pure Python unless noted.

requirements_dev.txt groupings:

    # Formatting
    black
    isort

    # Linting
    flake8
    flake8-bugbear
    flake8-pyproject
    pylint

    # Type checking
    mypy

    # Security
    bandit
    detect-secrets
    pip-audit
    safety

    # Testing and coverage
    coverage

    # Dependency hygiene
    pip-check

    # Workflow
    pre-commit

    # Code quality metrics
    interrogate
    radon
    vulture
    wily
    xenon


WHAT EACH TOOL DOES

Formatting:
  black         Opinionated auto-formatter. Run it first, before any linter.
  isort         Sorts import statements. Must be configured with profile = "black"
                or it will conflict with black's import formatting.

Linting:
  flake8        Style and simple error checking. Requires flake8-pyproject to
                read config from pyproject.toml.
  flake8-bugbear  Plugin that catches common buggy patterns: mutable default
                arguments, broad exception catches, useless expressions. Catches
                bugs at lint time before they become test failures.
  pylint        Deeper analysis than flake8: design issues, too-many-arguments,
                unused variables, etc. Expect overlap with flake8; both are
                worth keeping.

Type checking:
  mypy          Static type checker. Catches type errors before runtime.

Security:
  bandit        Scans source code for security issues: hardcoded passwords, weak
                crypto, shell injection risks, use of dangerous functions.
  detect-secrets  Scans for accidentally committed secrets (API keys, tokens,
                passwords). Critical in regulated and air-gapped environments.
                Requires a baseline file (see DETECT-SECRETS SETUP below).
  pip-audit     Checks installed packages against OSV and PyPI Advisory DB for
                known CVEs.
  safety        Checks against the Safety DB (PyUp). Complements pip-audit by
                using a different vulnerability database. Cross-checking reduces
                blind spots in regulated environments.

Testing and coverage:
  coverage      Measures test coverage. Use branch = true for branch coverage,
                which is more thorough than line coverage alone.

Dependency hygiene:
  pip-check     Verifies that all installed packages have their dependencies
                satisfied (checks for broken or incompatible installs). Different
                from pip-audit which checks for CVEs.

Workflow:
  pre-commit    Runs hooks automatically before each commit. All the above tools
                can be wired in as hooks.

Code quality metrics:
  interrogate   Measures docstring coverage (percentage of code that has
                docstrings). Useful for libraries and public APIs.
  radon         Computes cyclomatic complexity and maintainability index.
  vulture       Finds dead code (unused functions, variables, imports).
  wily          Tracks complexity trends over time using git history. Only
                meaningful once the project has history to compare.
  xenon         Enforces complexity thresholds using radon data. Blocks commits
                if complexity exceeds configured grades.


TOOL NOTES AND GOTCHAS

deptry is NOT a pure Python tool. It is written in Rust with a Python wrapper,
similar to ruff. If you require pure Python tools for cross-platform consistency
or air-gapped environments, use pip-check for dependency compatibility and accept
that no pure-Python replacement fully covers deptry's use case (checking that
your source code's imports match your declared dependencies in pyproject.toml).

isort and black conflict without configuration. Add to pyproject.toml:

    [tool.isort]
    profile = "black"
    line_length = 79

flake8 and black conflict on two specific checks:
  E203: whitespace before ':' -- black formats slices with spaces around the colon
  W503: line break before binary operator -- black prefers this style

Add to pyproject.toml:

    [tool.flake8]
    extend-ignore = ["E203", "W503"]

pylint line-too-long (C0301) is duplicate noise when black is also enforcing
line length. Disable it:

    [tool.pylint."messages control"]
    disable = ["C0301"]

Tab expansion false positives: flake8 and pylint default to 8-space tab expansion
(Unix standard) but most editors display tabs as 4 spaces. A deeply indented
line with tabs can appear 40 characters wide in the editor but 75+ to the linter.
Fix by setting indent-size in both tools to match your editor:

    [tool.flake8]
    indent-size = 4

    [tool.pylint.format]
    indent-after-paren = 4

Running black first eliminates this problem because black converts all tabs to
spaces before the linters see the file.

pre-commit works on both Linux and Windows. Shell script hooks (.sh) will fail
on Windows without Git Bash or WSL. Python-based hooks (all tools in this list)
work on both platforms without extra configuration.


DETECT-SECRETS SETUP

detect-secrets requires a one-time scan to create a baseline file. Run this
once in the project root and commit the result:

    detect-secrets scan > .secrets.baseline

After that, detect-secrets compares new scans against the baseline. Findings
already in the baseline are accepted; new ones block the commit. When a finding
is a confirmed false positive, update the baseline:

    detect-secrets scan --baseline .secrets.baseline


PRE-COMMIT HOOK TIERS

Split hooks into two tiers to reduce friction while still capturing metrics data:

Blocking (commit fails on violation): black, isort, flake8, pylint, mypy,
bandit, detect-secrets

Reporting only (output printed but commit succeeds): radon, wily, interrogate,
vulture

This lets you build familiarity with the metrics tools on small clean codebases
before they become friction on larger ones.


PYPROJECT.TOML CONFIGURATION

One pyproject.toml in the project root configures all tools. Key sections:

    [tool.black]
    line-length = 79
    target-version = ["py311"]

    [tool.isort]
    profile = "black"
    line_length = 79

    [tool.flake8]
    max-line-length = 79
    indent-size = 4
    extend-ignore = ["E203", "W503"]

    [tool.pylint.format]
    max-line-length = 79
    indent-after-paren = 4

    [tool.pylint."messages control"]
    disable = ["C0301"]

    [tool.mypy]
    python_version = "3.11"
    disallow_untyped_defs = true
    check_untyped_defs = true
    no_implicit_optional = true
    strict_optional = true
    warn_return_any = true
    warn_unused_configs = true
    warn_redundant_casts = true
    warn_unused_ignores = true

    [tool.bandit]
    skips = []

    [tool.coverage.run]
    branch = true
    omit = ["test/*", ".venv/*", "venv/*"]

    [tool.coverage.report]
    show_missing = true
    fail_under = 80

    [tool.vulture]
    min_confidence = 80

    [tool.interrogate]
    ignore-init-method = true
    ignore-magic = true
    fail-under = 80

    [tool.radon]
    cc_min = "B"

    [tool.xenon]
    max-absolute = "B"
    max-modules = "A"
    max-average = "A"

Complexity grades for radon and xenon run A (simplest) through F (untestable).
Setting cc_min = "B" in radon means only functions graded B or worse are
reported, keeping output focused on code that needs attention. Setting
max-absolute = "B" in xenon means no single function may be more complex than
grade B before xenon blocks the build.

bandit skips should always have a written justification comment. An empty skips
list is the correct default in a DevSecOps environment. Only add a skip when
a finding is a confirmed false positive, and document why.


VERSION PINNING

requirements_dev.txt does not pin versions. This is acceptable for development
tools since you generally want the latest. For air-gapped environments using a
private PyPI mirror, unpinned requirements can cause subtle differences between
machines if the mirror lags. In those cases, generate a pinned lockfile:

    pip-compile requirements_dev.txt -o requirements_dev.lock

Install from the lockfile on air-gapped machines for reproducibility.
